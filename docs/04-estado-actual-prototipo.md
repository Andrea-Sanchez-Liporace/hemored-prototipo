## Cómo leer este documento

Cada flujo se clasifica en uno de tres estados:

| Estado | Significado |
|---|---|
| 🟢 **Funciona hoy** | La pantalla está conectada a datos reales (lee y/o escribe contra `frontend/db/*.json` vía la capa JS) y el resultado se ve reflejado en la UI. |
| 🟡 **Diseñado, no conectado** | La UI existe y es funcional visualmente, pero no hay datos reales detrás — o el binding de lectura está hecho pero no llega a pantalla (ver "patrón silencioso" abajo). |
| 🔴 **Roto / inexistente** | El botón/formulario no ejecuta ninguna lógica real: no tiene `onclick`, o el handler que tiene no persiste nada, o literalmente hace lo mismo que "Cancelar". |

## El hallazgo estructural (antes de entrar flujo por flujo)

Verificado directamente en el código, no es un problema puntual de una pantalla:

- **`frontend/js/db.js`** solo tiene funciones de **lectura**: `init()`, `find()`, `where()`, `all()`. No existe `create`, `update` ni `delete` en ningún archivo del proyecto.
- **`frontend/js/sesion.js`**: el login está **hardcodeado** a 4 pares email/password fijos — no lee `usuarios.json` para autenticar. No existe ninguna función de registro.
- **`frontend/js/data.js`**: solo agrega funciones de lectura para armar dashboards (5 de las ~9 posibles: `cargarDashboardDonante`, `cargarMisTurnos`, `cargarMisDocumentos`, `cargarDashboardHospital`, `cargarTurnosHoy`, `cargarTurnosProfesional`, `cargarDashboardAdmin`). Cero funciones de escritura.
- **Cero usos de `localStorage` en todo `frontend/`** (verificado). No hay ningún mecanismo para que una acción del usuario sobreviva a un cambio de página o un refresh.

Sobre esto se apilan **tres patrones repetidos** en decenas de pantallas:

1. **Botón sin handler.** El elemento no tiene `onclick` ni listener — clickear no hace absolutamente nada (ej: "Crear cuenta" en registro de donante, "Marcar todas como leídas" en notificaciones, "Guardar" en varios perfiles).
2. **"Guardar" = "Cancelar".** El botón de acción primaria de un modal llama literalmente a la misma función que el botón "Cancelar" — el modal se cierra sin persistir nada (ej: Registrar donación, Cargar resultado, Emitir certificado, Emitir factura).
3. **Lectura conectada pero silenciosa.** La función de `data.js` corre de verdad, trae datos reales del JSON, pero el HTML no tiene los `id` que esa función busca para inyectar el resultado — no hay error visible, el dato simplemente se pierde. Pasa en **3 de los 4 dashboards principales**: `hospital/dashboard.html`, `admin/dashboard.html`, `profesional/dashboard.html` (el único que sí funciona parcialmente es el flujo de login/sesión).

### Capa de escritura propuesta (transversal a todo el proyecto)

Como no hay backend, la solución consistente para *todos* los gaps de escritura de este documento es la misma: extender `db.js` con dos funciones genéricas y persistencia en `localStorage`:

```js
// en frontend/js/db.js
function crear(tabla, objeto) {
  const id = Math.max(0, ...data[tabla].map(r => r.id)) + 1;
  const nuevo = { id, ...objeto };
  data[tabla].push(nuevo);
  _persistir();
  return nuevo;
}

function actualizar(tabla, id, cambios) {
  const row = find(tabla, id);
  if (row) Object.assign(row, cambios);
  _persistir();
  return row;
}

function _persistir() {
  localStorage.setItem('hemored_overrides', JSON.stringify(data));
}

// en init(), antes o después del fetch: mergear localStorage.getItem('hemored_overrides') si existe
```

Cada gap "🔴 Roto" de las tablas siguientes se resuelve construyendo una función específica de negocio (ej. `reservarTurno`, `crearCampana`, `aprobarHospital`) que valide reglas propias y llame a `crear`/`actualizar` por debajo. Por eso no repetimos el boilerplate de `localStorage` en cada fila — solo la función de negocio puntual.

## Componente compartido: select personalizado (agregado 2026-09-15)

**No es de un rol en particular — aplica a los 64 `<select>` de las 26 pantallas del sitio que ya cargan `js/ui.js`.** La usuaria pidió cambiar el color de resaltado (el azul del sistema operativo) por el rosa/morado de la marca. Investigado antes de tocar nada: **ningún navegador permite estilizar con CSS el color de las opciones dentro del popup nativo de un `<select>`** — Chrome y Safari lo dibujan como un widget del sistema operativo, totalmente fuera del alcance de la página; Firefox permite un poco más pero tampoco de forma confiable. Se le presentaron dos caminos a la usuaria: dejarlo con el look nativo, o reemplazar el `<select>` en todo el sitio por un componente propio. **Eligió la segunda.**

**Diseño, para no reescribir la lógica de las 26 pantallas que ya leen/escriben `.value` en un select:** `HemoRed.ui.mejorarSelects()` (llamada automática dentro de `HemoRed.ui.init()`, que ya corría en cada pantalla) recorre todos los `<select>` del documento y, para cada uno:
1. Inserta un `<button>` justo al lado, con las MISMAS clases (y el mismo `style` inline, si lo tenía) que el select original — así hereda automáticamente el mismo tamaño/borde/tipografía sin duplicar ningún CSS.
2. Oculta el `<select>` real (`opacity:0`, saca de flujo con `position:absolute`, `pointer-events:none`) — pero **a propósito no le achica el tamaño a 0** para que herramientas como Playwright (`selectOption()`) lo sigan encontrando "visible" y puedan seguir interactuando con él directo, sin tener que tocar ningún test existente.
3. Intercepta `.value`, `.selectedIndex` y `.disabled` con `Object.defineProperty` — el resto de la app precarga selects todo el tiempo con asignaciones directas (`elemento.value = x`, ej. al restaurar un perfil guardado), y eso NO dispara ningún evento nativo; sin este interceptor el botón se quedaría mostrando contenido viejo.
4. Al abrir el botón, arma una lista (`.hr-select-panel`, agregada a `<body>` para no quedar recortada por ningún contenedor) con el resaltado en rosa pálido (`--color-rosa-pale`, la misma variable que ya usan `.turno-opt.selected`/`.sangre-opt.selected` en el resto del sitio — no es un color nuevo). Elegir una opción actualiza el `<select>` real (a través del setter interceptado) y dispara un evento `change` real, así el `onchange="..."` que ya tenía cada select en su HTML sigue funcionando sin cambios.

**Bug real #1, encontrado y corregido durante la implementación:** el panel se abría y se cerraba solo en el mismo click — el listener que cierra el panel al clickear "afuera" comparaba `e.target === trigger`, pero el click en realidad cae sobre el `<span>`/`<i>` de adentro del botón, no sobre el `<button>` en sí. Corregido a `trigger.contains(e.target)`.

**Bug real #2, más grave, encontrado por la usuaria (2026-09-15, segunda vuelta) al pedir que se sumaran `publico/pago.html` y `publico/contacto.html` y se revisara que sus contenedores no tuvieran scroll horizontal:** el `<select>` real oculto (`position:absolute`, sin tamaño 0 a propósito, ver arriba) generaba scroll horizontal en **cualquier pantalla del sitio cuyos selects usaran la clase `.form-input`** (no solo en las 2 páginas nuevas) — `perfil.html`, `dashboard.html` y varias más de Hospital/Admin también estaban afectadas, solo que nadie lo había notado todavía. Causa: casi ningún contenedor del sitio tiene `position:relative`, así que un elemento `position:absolute` sin ancestro posicionado resuelve sus porcentajes contra el viewport completo (el "initial containing block"), no contra su contenedor original — el `width:100%` que `.form-input` le daba al select terminaba estirando el elemento invisible hasta cubrir TODA la página. Corregido forzando `.hr-select-native` a un tamaño fijo de 1×1px (sigue siendo un bounding box "no vacío", suficiente para que Playwright pueda seguir usando `selectOption()`) en vez de heredar `width:100%`. Se verificó con un barrido automatizado sobre las 26 pantallas del sitio en 3 anchos (375/768/1280px): sin este fix había overflow en `perfil.html`, `dashboard.html`, `mis_turnos.html`, `mis_documentos.html`, `campana_detalle.html`, `formularios_predonacion.html` y varias de Hospital — después del fix, cero.

**Hallazgo aparte, NO relacionado con el select, encontrado de paso durante ese mismo barrido y no corregido en esta vuelta:** varias pantallas de Hospital y Admin con contenido en tablas/grillas (`hospital/profesionales.html`, `hospital/pacientes.html`, `hospital/nueva_campana.html`, `admin/metricas.html`, `admin/donantes.html`, entre otras) ya tenían scroll horizontal en mobile (375px) **antes** de este cambio — se confirmó ocultando manualmente todos los elementos del select personalizado y viendo que el overflow seguía exactamente igual. Es un problema de responsive preexistente de esas pantallas (probablemente contenido de ancho fijo sin breakpoint mobile, mismo patrón de bug que ya se encontró y corrigió puntualmente en `donante.css` en sesiones anteriores), no algo que haya empezado con el select personalizado. Queda anotado acá para no perderlo, sin tocar — es un trabajo de responsive bastante más grande, pantalla por pantalla, que no se pidió en esta vuelta.

**Alcance real, actualizado (no es 100% del sitio):** ahora cubre los 26 archivos que cargan `js/db.js` + `js/ui.js`, incluyendo `publico/pago.html` y `publico/contacto.html` (se les agregaron esos 2 scripts únicamente para esto — son mockups 100% estáticos del circuito "registro de hospital → pago → aprobación", todavía sin conectar, que antes no cargaban nada de `HemoRed`; no se llama a `HemoRed.db.init()` en ninguna de las dos, siguen sin datos reales).

**Bug real #3, reportado por la usuaria después de subir el fix del #2 ("sigo teniéndolo, mira la regla css para todas las medidas de viewport"):** el scroll horizontal seguía apareciendo, pero esta vez **adentro del propio panel desplegable**, no en la página. Causa: `posicionarPanel()` fijaba el ancho del panel EXACTO al del botón (`panel.style.width = trigger.width`) — para un botón angosto como "Provincia" (~100px), una opción larga como "Santiago del Estero" no entraba, y como `.hr-select-panel` ya tenía `overflow-y:auto`, el navegador agrega `overflow-x:auto` solo (regla real del spec de CSS: si un eje no es `visible` y el otro sí, el que era `visible` pasa a `auto` — nunca se pidió esto a propósito). **Primer intento de arreglo (después revertido):** dejar que el panel crezca más ancho que el botón (`min-width` en vez de `width` fijo). La usuaria lo rechazó — un panel bastante más ancho que un botón chico se veía desproporcionado. **Segundo intento (también revertido):** mantener el panel del mismo ancho que el botón, pero con el texto largo pasando a una segunda línea (`white-space: normal`). Tampoco sirvió: al no cortar por palabra completa, partía nombres a la mitad ("Catamarc" + "a" en dos líneas), se veía roto. **Arreglo final:** ensanchar el CAMPO en sí (`.filter-select` en `donante.css`/`hospital.css`/`admin.css`, `min-width: 200px`, contra los ~100-130px que tenía antes) para que el contenido más largo entre cómodo en una sola línea (`white-space: nowrap` en `.hr-select-option`, sin partir palabras) — el panel simplemente copia el ancho del campo (`panel.style.width = trigger.width`, sin `min-width` ni crecimiento propio), así quedan siempre del mismo ancho y proporcionados entre sí. También se agregó un ajuste de posición para que, si el panel se saldría de la pantalla por la derecha (casos extremos), se corrija en vez de generar scroll.

**Bug real #4, encontrado al verificar el #3 (nadie lo había reportado todavía):** al scrollear DENTRO del panel para llegar a las opciones de más abajo (la lista de 24 provincias no entra completa en los 260px de alto), el panel se cerraba solo. Causa: el listener que cierra el panel al scrollear la página de atrás (`window.addEventListener('scroll', ..., true)`, en fase de captura) no distinguía si el scroll venía de la página o de adentro del propio panel — cualquiera de los dos lo cerraba. Corregido para ignorar el scroll cuando el `event.target` está adentro del panel abierto.

**Nota de proceso, por si se repite algo similar:** el primer reporte de este bug (#3) no se pudo reproducir al toque porque el servidor local de pruebas manuales (`python -m http.server`) no manda headers para evitar el cache del navegador — se armó `tests/_dev_server_no_cache.py` (mismo servidor, pero con `Cache-Control: no-store` en cada respuesta) para las revisiones manuales de acá en adelante. **Importante: no correr ese servidor al mismo tiempo que la suite automatizada** — compartir el puerto 8791 entre los dos generó lentitud real que hizo fallar 2 tests por timeout (no por bugs de código; se confirmó volviendo a correr la suite sola, sin el servidor manual, y quedó 28/28 en verde).

Test: `tests/select-personalizado.spec.js` (9 casos en total — se agregaron los de scroll horizontal de página, scroll horizontal interno del panel, y que el panel se pueda scrollear sin cerrarse).

### Solicitudes de corrección sobre certificados de donación (cerrado 2026-09-08, flujo de 2 roles)

**Origen:** al conectar "Mis documentos", el botón "Enviar observación" quedó funcional del lado del donante pero **no persistía nada** (no existía tabla). Se reemplazó por un flujo completo: modal con un checkbox por cada campo "reportable" del certificado — al marcar uno, se muestra el valor actual (solo lectura) al lado de un campo en blanco para la corrección propuesta — y una pantalla nueva del lado del Hospital para revisar, aprobar (aplica el cambio real) o rechazar (con motivo obligatorio).

**Tabla real: `solicitudes_correccion`** — `id (PK)`, `usuario_id (FK)`, `hospital_id (FK, resuelto del certificado al crear la solicitud)`, `certificado_id (FK a certificado_donacion)`, `campos` (lista de `{ campo, valor_actual, valor_propuesto }`), `estado ('pendiente'|'aprobada'|'rechazada')`, `fecha_solicitud`, `resuelto_por (FK, null hasta resolver)`, `fecha_resolucion (null hasta resolver)`, `motivo_rechazo (null salvo rechazo)`.

**Campos reportables (mapa `CAMPOS_CORREGIBLES` en `js/data.js`, comparte la misma definición entre donante y hospital):** nombre, apellido, DNI (→ `usuarios`), fecha de donación (→ `certificado_donacion`). "Nombre del donante" se separó en `nombre`/`apellido` (dos campos reportables distintos) para que cada uno mapee sin ambigüedad a `usuarios.nombre`/`usuarios.apellido` al aprobar. **Volumen donado, profesional a cargo y hospital NO son reportables** (decisión 2026-09-08): son datos que carga el sistema/hospital en el momento de la donación, el donante no los controla ni puede saber si están mal desde su lugar. De paso, "Volumen donado" tampoco se muestra ya en la vista del certificado del donante (no era un dato que correspondiera mencionar ahí).

**Nombre y DNI siguen siendo reportables acá aunque viven en `usuarios` (el perfil), no en el certificado puntual** — se mantuvo la decisión original: un solo lugar donde el donante reporta cualquier error, en vez de mandarlo a editar el perfil por separado. Al aprobar, el cambio se aplica igual sobre `usuarios`.

**Qué hace `HemoRed.data.resolverSolicitudCorreccion()` al aprobar:** agrupa los campos marcados por tabla de destino (`usuarios` o `certificado_donacion`) y aplica cada uno con `HemoRed.db.actualizar()` — no alcanza con marcar la solicitud como aprobada, el dato cambia de verdad. Mientras una solicitud sigue `pendiente` para un certificado, no se puede mandar una segunda para el mismo (se rechaza con un error).

**Estado visible del certificado (agregado 2026-09-08, segunda vuelta):** no es un campo nuevo en `certificado_donacion` — se calcula al vuelo contra la última solicitud de ese certificado (`ultimaSolicitudCertificado()` en `mis_documentos.html`). 3 estados, badge en la lista de "Mis documentos" + detalle:
- Sin solicitud, o última `rechazada` → **"Emitido"** (rechazar no deja marca: el certificado no cambió, vuelve a la normalidad).
- `pendiente` → **"En revisión"**.
- `aprobada` → **"Emitido con corrección"**.

En cualquiera de los 3 estados, el detalle del certificado muestra el desglose completo de la última solicitud (cada campo reportado, valor actual tachado vs. propuesto), la fecha y hora en que se solicitó (`fecha_solicitud`) y, si ya se resolvió, la fecha y hora de la resolución (`fecha_resolucion`) — ambos campos ya existían en la tabla desde el diseño original, solo faltaba mostrarlos. No se pierde el historial del pedido aunque ya esté resuelta. Mientras hay CUALQUIER solicitud registrada (pendiente, aprobada o rechazada), no aparece un botón para reportar de nuevo — solo aparece "Reportar dato incorrecto" si el certificado nunca tuvo ninguna solicitud.

**Del lado del donante** (`mis_documentos.html`): el botón "Reportar dato incorrecto" reemplaza al viejo "Enviar observación", solo en la vista de certificado — es el único lugar de todo el archivo donde aparece (la pestaña "Consentimientos", que en su momento tampoco lo tenía, se sacó por completo el 2026-09-15, ver esa fila más arriba).

**Del lado del hospital** (`hospital/documentacion.html`): se agregó una 3ª pestaña "Solicitudes de corrección" (con badge de pendientes) a la misma pantalla existente, en vez de crear un archivo nuevo. `cargarSolicitudesCorreccion()` resuelve el hospital logueado igual que ya lo hace `cargarDashboardHospital()` (`usuarios.hospital_id`). El modal de revisión muestra cada campo tachado (actual) vs. propuesto, y exige motivo para rechazar.

**Al rechazar, se genera una notificación real** en la tabla nueva `notificaciones_donante` (ver esa fila en Donante y `docs/01`) con el mismo motivo que el hospital escribió al rechazar — reutiliza el apartado "Notificaciones" que ya estaba planeado como próximo hito del donante, en vez de inventar un mecanismo de aviso aparte. El certificado en sí también deja ver el mensaje "Corrección no aplicada" con un botón "Ver notificaciones". **Pendiente para más adelante, decisión explícita de la usuaria:** que el hospital pueda redactar un mensaje libre (tipo mail) en vez de que la notificación solo repita el motivo del rechazo — hoy no hace falta, porque el motivo que ya escribe al rechazar alcanza para generar la notificación automáticamente.

#### Investigación: cómo validar el email del donante (investigado 2026-09-10, sin implementar)

**El patrón estándar de la industria es "verification link" — y ya usamos exactamente este mecanismo en otro lugar del proyecto:**
1. Al registrarse, el usuario queda creado con `email_verificado: false`.
2. El backend genera un token de un solo uso con expiración (ej. 24-48hs), lo asocia al usuario, y le manda un mail real a su casilla personal con un link tipo `https://hemored.com/verificar-email?token=XXXX`.
3. El usuario abre SU correo (fuera de la app) y hace click.
4. El backend valida el token (existe, no expiró, no fue usado ya), marca `email_verificado: true`, y lo invalida para que no se reuse.
5. Mientras no esté verificado, se puede restringir funcionalidad — **recomendación: no bloquear el login** (no trabar el onboarding), pero sí bloquear "Reservar turno" con un banner visible hasta verificar.

**Es el mismo patrón que ya implementamos para el token de `formulario_postdonacion` (F4)** — de un solo uso, con expiración, validado contra una tabla antes de aceptar la acción. No hace falta inventar nada nuevo conceptualmente, solo aplicar la misma idea a un caso distinto.

**Herramientas para cuando exista el backend (Django + DRF, según lo ya definido en "Arquitectura propuesta"):**
- **`django-allauth`** — la librería más usada y completa para autenticación en Django; trae verificación de email lista para usar (generación de link, template, endpoint de confirmación), y de paso resuelve login social si algún día hiciera falta.
- **`djoser`** — pensada específicamente para proyectos DRF + JWT (que es exactamente nuestro stack planeado: "API REST... autenticación JWT", ver arriba); expone endpoints REST listos para activación de cuenta por email, en el mismo estilo `/api/{recurso}` que ya está definido acá.
- **A mano, sin librería de terceros:** Django ya trae `django.core.signing` (tokens firmados con expiración, sin necesitar tabla nueva) o se puede adaptar el mismo mecanismo que usa `django.contrib.auth` para resetear contraseña (`PasswordResetTokenGenerator`). Menos dependencias, más trabajo manual.

**Envío real del mail — Django no manda mails de verdad por sí solo en producción, hace falta un servicio:**
- Desarrollo/pruebas: `EMAIL_BACKEND` de consola de Django — imprime el mail en la terminal, sin mandar nada real, útil para probar el flujo.
- Producción — servicios transaccionales típicos (pensados para pocos mails automáticos, no marketing masivo): **SendGrid**, **Amazon SES**, **Mailgun**, o **Resend**. Todos con un tier gratuito chico, suficiente al principio. `django-anymail` es la librería que unifica la integración con cualquiera de ellos sin atarse a un proveedor específico desde el primer día.

**Cómo se vería concretamente en HemoRed:**
- Nuevo servicio o extensión de `/api/auth` (ver "Servicios v1 (MVP)" más abajo): un endpoint para reenviar el mail de verificación y otro para confirmar el token.
- El link del mail apuntaría a una pantalla nueva del frontend (`publico/verificar_email.html`), con el mismo patrón que ya usa `postdonacion_anonimo.html`: leer `?token=` de la URL y llamar al backend — la diferencia es que acá si hace falta sesión (es sobre la cuenta ya logueada), a diferencia de F4 que es anónimo a propósito.

#### Investigación: cómo validar el DNI del donante (investigado 2026-09-10 — arquitectura en capas, SE IMPLEMENTA al arrancar el backend)

**RENAPER (Registro Nacional de las Personas) tiene un servicio real: el Sistema de Identidad Digital (SID).** Permite validar identidad contra el padrón nacional vía API REST (confronte de datos + biometría facial contra la foto del DNI). No es de acceso libre/self-service: cualquier entidad, pública o privada, que quiera usarlo tiene que tramitar el **Convenio Único de Confronte de Datos** (vía TAD, Trámites a Distancia), demostrar "interés legítimo" (lo evalúa RENAPER) y cumplir la Ley 25.326 de Protección de Datos Personales. Aparte existe **Mi Argentina / ValidAR**, la app donde el ciudadano valida su propia identidad (foto del DNI + selfie con prueba de vida) para trámites y credenciales digitales del Estado — es un frontend para la persona, no un servicio que una app de terceros pueda invocar directo sin convenio.

**Proveedores privados que ya resolvieron ese convenio y lo revenden como servicio (identity verification / KYC-as-a-service):**
- **Didit** — integración documentada con RENAPER: valida DNI + biometría facial contra el padrón oficial, devuelve `Full_Match`/`Partial_Match`/`No_Match`. Cobra por verificación (aprox. USD 0,20 el confronte de datos, desde USD 0,30 con selfie/prueba de vida).
- **MetaMap** — verificación oficial de DNI para Argentina, con cruce contra AFIP y facematch, dentro de su plataforma para LATAM.
- Modelo de costo general de estos proveedores: **pago por verificación** (o planes por volumen), vía API REST/SDK, sin que HemoRed tenga que tramitar el convenio directo con RENAPER — el proveedor ya lo tiene y lo revende.

**Decisión de la usuaria (2026-09-10): validar el DNI en capas, no en un solo paso — cada capa resuelve un problema distinto, y hay que tenerlas claras para no confundir "validamos algo" con "validamos identidad de verdad".**

**Capa 1 — OCR propio de las fotos del DNI (frente y dorso), como pre-chequeo antes de gastar la consulta paga.** El donante sube 2 fotos (frente y dorso de su DNI); el sistema extrae nombre, apellido, DNI y domicilio, y los compara contra lo que tipeó en el formulario.
- **El DNI argentino actual (tarjeta plástica) sí tiene todos estos datos impresos** — no es algo que se haya perdido con la libreta vieja. Frente: foto, nombre, apellido, sexo, nacionalidad, fecha de nacimiento, número. Dorso: **domicilio**, CUIL, lugar de nacimiento, huella dactilar impresa, y un **código de barras 2D (PDF417)** que codifica varios de esos mismos datos de forma estructurada.
- **Cómo leerlo:** decodificar el código de barras PDF417 es lo más confiable (hay librerías genéricas gratuitas para eso, formato fijo y estructurado) — usarlo como fuente principal. Como respaldo para lo que no esté en el código de barras, OCR de texto libre con **Tesseract** (open source, gratis) — en el navegador vía **Tesseract.js** (corre 100% client-side, sin backend, coherente con cómo está armado el resto del prototipo) o server-side en Django si se prefiere. Precisión: aceptable, pero cae con fotos de celular mal encuadradas/con reflejo del plástico laminado — no esperar 100% de éxito en todos los casos.
- **Nota para 2026 en adelante:** RENAPER empezó a emitir en paralelo un DNI electrónico nuevo (chip + QR/Data Matrix en vez de PDF417) — de adopción voluntaria, el formato viejo sigue siendo válido, así que el lector eventualmente tendría que soportar los dos formatos.
- **Qué valida esta capa y qué NO:** valida **consistencia de datos** — ¿lo que dice la foto coincide con lo que el usuario tipeó? Atrapa errores de tipeo, o alguien subiendo un DNI que no es el que puso en el formulario. **NO valida identidad**: cualquiera puede subir la foto del DNI de otra persona (real o editada) y el OCR "valida" igual, porque solo compara texto contra texto, no contra ninguna base de datos externa ni contra quién está efectivamente del otro lado de la pantalla.
- **Domicilio:** se le muestra al donante el domicilio leído y se le pregunta si sigue siendo el actual. **Esto no es una validación técnica, es una autodeclaración** — no hay forma de confirmar el domicilio real sin otra fuente (factura de servicio, RENAPER). Documentarlo así, no como algo verificado.

**Capa 2 — confronte de datos contra RENAPER, vía Didit/MetaMap** (ya investigado arriba): confirma que el DNI+nombre+fecha de nacimiento existen juntos en el padrón nacional — un nivel más fuerte que el OCR propio porque compara contra una fuente externa real, no solo contra lo que el usuario tipeó.
- **Importante — esta capa TAMPOCO resuelve la suplantación de identidad.** Si alguien carga los datos reales y válidos de otra persona (ej. de un familiar), el confronte de datos simple devuelve "válido" igual — porque técnicamente los datos SON válidos, aunque quien los cargó no sea el dueño. Este punto lo marcó la usuaria explícitamente al revisar el análisis, y es real: ni el OCR propio ni el confronte de datos por sí solos evitan que alguien se registre con la identidad de otra persona.

**Capa 3 (opcional, la única que resuelve suplantación de identidad) — biometría facial con prueba de vida ("liveness"), selfie en el momento comparada contra la foto oficial del DNI.**
- Es el nivel más caro de Didit/MetaMap (desde ~USD 0,30) y el único que efectivamente refuta "cargué los datos de mi hermana pero la cara que aparece en la selfie es la mía, no la de ella".
- **Se evaluó usar huella dactilar en vez de cara, por mejor experiencia de usuario — no es viable de forma remota.** El sensor de huella del celular está diseñado para que la huella nunca salga del dispositivo (queda en un chip aislado tipo Secure Enclave); lo único que expone a una web es un "sí/no" local (WebAuthn/FIDO2), sin acceso al dato biométrico ni forma de compararlo contra RENAPER. RENAPER sí ofrece verificación por huella, pero para trámites presenciales con lector dedicado (bancos, ANSES) — no hay ningún servicio para que el usuario suba su huella desde su casa. Por eso toda la industria de verificación remota (Didit, MetaMap, Onfido, Veriff) usa cara y no huella: es el único dato biométrico que ya está en el bolsillo de todo el mundo (la cámara), sin hardware extra.
- **Liveness pasivo, no activo, por experiencia de usuario.** Liveness *activo* (girar la cabeza, parpadear, sonreír a pedido) es más tedioso — fue la experiencia que la usuaria probó y calificó como mala. Liveness *pasivo* analiza una sola foto/frame con IA para detectar spoofing (foto de una foto, pantalla, máscara) sin pedirle nada al usuario más allá de sacarse una selfie común — mucho menos fricción, y Didit/MetaMap lo ofrecen como modo de configuración (no hace falta el modo activo).
- **Por qué conviene pagar Didit/MetaMap para esto, en vez de resolverlo gratis por cuenta propia — el costo adicional se justifica:** se buscó específicamente una alternativa gratuita/open source al liveness pasivo pago, y **no se encontró una versión gratuita actualizada que lo reemplace con garantías reales.** La única opción libre real, **DeepFace** con el parámetro `anti_spoofing=True` (que usa el modelo open source **Silent-Face-Anti-Spoofing**, MiniVision AI), **no tiene actualizaciones desde 2020-2021** — quedó entrenado únicamente contra ataques de spoofing relativamente simples (foto impresa, foto de pantalla), sin ninguna defensa actualizada contra máscaras 3D o deepfakes, que sí son un vector de ataque real hoy. Los tiers gratuitos de las nubes grandes tampoco cubren esto: AWS Rekognition Face Liveness cobra desde el primer chequeo, Azure excluye liveness de su free tier general, Google Cloud Vision directamente no lo ofrece. **Conclusión: no hay atajo gratuito confiable para esta capa** — Didit/MetaMap invierten específicamente en mantener sus modelos al día contra técnicas de fraude nuevas (reentrenamiento continuo), que es exactamente lo que un modelo estático y abandonado no puede ofrecer. El costo adicional (desde ~USD 0,30 por verificación) compra seguridad real, no es sobreprecio por lo mismo.
- **No queda para implementar ahora ni para la demo — se diseña e implementa en la etapa de desarrollo del backend, igual que las Capas 1 y 2.** Esta investigación deja resuelto el "con qué" (Didit/MetaMap, nivel biométrico) y el "por qué" (sin alternativa gratuita viable), para no tener que reabrir la discusión cuando se llegue a esa etapa.

**Resumen del alcance a implementar cuando arranque el backend:** las 3 capas se diseñan e implementan en esa etapa, ninguna se toca en el prototipo actual ni se resuelve con una versión "de demo" mientras tanto. Capa 1 (OCR propio, frente+dorso) y Capa 2 (confronte de datos vía Didit/MetaMap) quedan como el alcance base comprometido. La Capa 3 (biometría/liveness, la única que resuelve suplantación de identidad) queda documentada con la herramienta recomendada (Didit/MetaMap, nivel biométrico) y el motivo del costo adicional — se investigó una alternativa gratuita (DeepFace + Silent-Face-Anti-Spoofing) y se descartó por estar desactualizada desde 2020-2021, sin garantías reales contra fraude actual.

**No confundir esto con Master Patient Index (MPI)** — son problemas distintos: esto valida que el DNI sea real y pertenezca a la persona (contra una fuente externa, RENAPER); el MPI resuelve algo completamente distinto (detectar que dos registros *internos* de HemoRed son la misma persona) y no confirma identidad contra nada externo. **Los dos se implementan al arrancar el backend** (decisión firme de la usuaria) — ver la comparación completa en `docs/01`, sección "Master Patient Index / EMPI".

## Matriz de dependencias entre roles

**Por qué existe esto:** varias pantallas ya cerradas (de cualquier rol) son de solo lectura, o de validación, sobre tablas que **otro rol distinto es el único que puede escribir**. Cerrar una pantalla no hace que el dato varíe — el rol que lee puede ver/usar lo que exista, y hoy existe poco porque casi ningún flujo de escritura de Hospital, Profesional o Super Admin está conectado todavía. Esta matriz evita dos errores: (a) pensar que una pantalla de solo lectura recién cerrada "no funciona" porque no trae datos nuevos, y (b) al cerrar una pantalla de escritura, olvidarse de que hay otra pantalla ya cerrada (de otro rol) que va a empezar a mostrar datos reales gracias a eso.

**Verificado contra el código real (2026-09-10), última revisión tras cerrar F4 + "Registrar donación"** — existen funciones de escritura reales para: `usuarios` (Donante, su propio perfil/registro; Hospital, al aprobar una corrección de nombre/apellido/DNI de un certificado), `turnos` (Donante crea, Hospital confirma/rechaza/completa vía `registrarDonacion()`), `formulario_consentimiento` (Donante, F1/F2 — sin escritura de Hospital, "Solicitudes de corrección" es exclusivo de certificados), `donaciones` (Hospital, `registrarDonacion()`), `certificado_donacion` (Hospital, al aprobar una corrección de sus campos), `solicitudes_correccion` (Donante crea, Hospital resuelve), `notificaciones_donante` (Hospital, al rechazar una corrección o al registrar una donación) y `formulario_postdonacion` (Hospital genera el token, Donante responde sin sesión). ## Hoja de ruta sugerida

No es la única forma de ordenar esto, pero así es como priorizaría dado lo relevado:

### Paso 0 — Infraestructura (desbloquea casi todo lo demás)
Implementar `crear()` / `actualizar()` + persistencia en `localStorage` en `db.js` (ver sección "Capa de escritura propuesta" arriba). Sin esto, ningún flujo de escritura de la lista puede cerrarse.

### Paso 1 — Quick wins (bajo esfuerzo, alto impacto visual)
Los 3 dashboards con "lectura silenciosa" (`hospital/dashboard.html`, `admin/dashboard.html`, `profesional/dashboard.html`) más `donante/mis_turnos.html` y `donante/mis_documentos.html`: la lógica de lectura **ya existe y funciona**, solo falta agregar los `id` al HTML y cablear el render. Ningún flujo de escritura involucrado.

### Paso 2 — Flujos Must Have del MoSCoW (núcleo del producto)
Según la priorización ya definida en `docs/01-relevamiento-requisitos.md`: registro de donante, reserva de turno, creación de campaña (los 3 pasos), gestión de turnos por el hospital (confirmar/rechazar). Sin esto, el "camino feliz" completo (donante se registra → busca campaña → reserva turno → hospital gestiona) no se puede demostrar de punta a punta.

### Paso 3 — Cierre del círculo institucional
Registro de hospital → pago → cuenta pendiente → aprobación por super admin. Hoy cada mitad de este flujo existe pero no se tocan entre sí.

### Paso 4 — Should Have
Historial de donaciones, documentación (resultados/certificados con el insert dual a `documentos`), facturación (ambos lados: hospital paga, admin emite/marca pagada), mensajería hospital↔HemoRed (falta hasta la vista).

### Paso 5 — Podría esperar
Métricas con agregación real (hoy son gráficos de relleno, visualmente ya "funcionan" para una demo), gestión de pacientes/profesionales del lado hospital.

### Paso 6 — v2
El módulo de atención clínica del profesional (F1-F4). Es grande pero autocontenido — se puede abordar como un bloque separado una vez que el resto del MVP esté cerrado, ya que la UI ya está prácticamente lista y "solo" falta la capa de persistencia.
